An API documentation checklist for agency-built integrations in South Florida

The integration works on launch day. Eight months later the client changes agencies, a new developer opens the repository, and the only documentation is a chat thread from someone who has since left.

This checklist is how Jason Colapietro and the Suede AI team document the APIs we run in production. It is written for agencies in West Palm Beach, Jupiter and the rest of Palm Beach County that build integrations for clients: a booking system feeding a CRM, a payment webhook, an inventory sync between a shop and its website. Each item points to the page on this site where it is already done, so you can look at a finished version before you write your own.

Why handoff is the real test in Palm Beach County

Much of Palm Beach County runs on a season. Restaurants, marinas, clinics and property managers here do a large share of their year between November and April, and that is exactly when nobody can afford a broken sync. Agencies turn over clients and staff like anywhere else, so an integration only one developer understands is a liability that tends to come due in the busiest month. Good API docs are what let the agency, the client and the next developer keep working when the original author is unavailable.

Jason Colapietro's rule for Suede is that the docs are finished when someone who did not build the integration can make one successful call and handle one failure without asking a question. The seven groups below are what it takes to get there.

The checklist

1. Base URL, authentication and a first request

  • One base URL per environment, written out in full, with staging and production listed separately.
  • How to authenticate, where the credentials live (the vault or secret name, never the value) and who is allowed to rotate them.
  • A copy-paste first request that works from a clean terminal. The Suede quickstart does this for a paid call: read the 402 challenge, sign, retry, then poll the job.

2. Every endpoint, with a captured example

  • Method, path, required and optional fields, and a real response captured from a live call, with the date it was captured. The endpoint reference on this site dates every example to 2026-10-11.
  • Prices or quotas where they apply, linked to the document they came from, so nobody has to trust a number copied into a slide.

3. Errors, and what to do about each one

  • A status-code table with a "what to do" column, not just a definition. The errors and limits guide has one row per code.
  • The machine-readable codes a client should branch on. On Suede those are rate_limited and unsupported_api_version.
  • Which requests cost nothing. For a client billed per call or per message, this one line heads off most billing disputes.

4. Retries, idempotency and rate limits

  • Name the idempotency header and its window. Suede uses X-Idempotency-Key, up to 200 characters, on every paid POST, so retrying a timeout never charges twice.
  • Rate-limit headers with a real example value. On 2026-10-11, unpaid requests to the Suede API carried a quota of 20 requests per 60-second window.
  • For webhooks: the retry schedule, how to verify the signature, and how to replay an event by hand after an outage.

5. Versioning and change notices

  • How versions are named, what counts as breaking, and how much notice clients get. Suede sends Deprecation and Sunset headers at least 90 days before a version is withdrawn.
  • A dated changelog that lives in the repository, not in someone's inbox.

6. A machine-readable copy

  • An OpenAPI file that matches the prose and is served by the API itself. The discovery guide lists Suede's openapi.json next to the MCP server and the agent card.
  • If AI agents will call the API, one name per action everywhere: the operation id, the tool name and the docs heading.

7. Ownership and sources

  • Who owns the integration on the agency side and on the client side, written as a role address rather than a person's name.
  • A Sources section on every page that names what it was checked against and when.

Test the docs the way an agent would

Before handoff, give the docs to someone who did not write the integration, or to a coding assistant with no other context, and ask for one successful call and one handled error. Every question they ask is a missing line. Coding assistants are now the first reader for many integrations, and a page an assistant can follow on the first try is a page a junior developer in Jupiter can follow too.

This is the same proof-first habit Jason Colapietro applies to agent output across the Suede AI sites. The Claude Code Field Notes piece on why agent-written code needs proof covers the checks to run after a deploy lands, and the Agentix guide on how to grade an AI agent before you deploy it applies the idea to agents that will be calling your client's API.

The tradeoffs

Captured examples go stale. Every dated response is a promise to recheck it when the API changes, and on this site that means rechecking the guides whenever the catalog moves. The full checklist is too much for a two-endpoint webhook; for a small integration, groups 1, 3 and 7 cover most of the risk. And documentation does not replace monitoring. An alert on the error rate catches a broken sync on a Saturday in February long before anyone reads a page.
