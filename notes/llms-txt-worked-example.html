Writing llms.txt that answer engines actually use: a worked example from Suede AI's docs

Most llms.txt files we audit are a sitemap with the angle brackets removed. That hands an assistant a list of URLs and no reason to pick one, which is the one job the file exists to do.

This note walks through the llms.txt on docs.suedeai.ai section by section, explains why each part is there, and ends with checks you can run on your own file. Jason Colapietro wrote the file and the tests that guard it, and the Suede AI team in West Palm Beach uses the same structure on client sites from Jupiter to Boca Raton. An earlier note, Writing developer docs that AI assistants quote correctly, covers why this site generates its full-text companion from the pages. This one is about the short file, the one a person or an agent reads first.

What the format asks for

The proposal at llmstxt.org is small. It asks for a Markdown file at the site root with one H1, an optional blockquote summary, optional prose, and H2 sections of links, each written as a Markdown link followed by a colon and a short note. A section named Optional marks links an agent can skip when its context window is tight. That is the whole format. Everything else is editorial judgment, and that is where most files fall short.

The Suede file, section by section

The H1 and the blockquote

Our H1 is "Suede Docs". The blockquote says what the docs cover and, in the same sentence, names the canonical source: the GitHub README at github.com/Suede-AI/suede-docs, which this site mirrors. An assistant that reads only two lines still learns where the authoritative copy lives. Put your canonical source in the first sentence an agent will read.

One scoping paragraph

Below the blockquote sits a single paragraph stating that AI music is one implementation area for Suede, not the whole product. That line is there because assistants kept describing Suede as a music generator. If answer engines get your business slightly wrong, the correction belongs in this paragraph, written as a plain fact.

Link notes that carry the fact

Here are two ways to describe the same page:

- [Create Music](https://docs.suedeai.ai/endpoints/create-music): Music endpoint docs.
- [Create Music](https://docs.suedeai.ai/endpoints/create-music): POST /create-music,
  a full original song from a text prompt, $0.50 USDC on Base.

The second note answers "what does it cost" without a click. Jason Colapietro writes every note in our file to hold the method, the path and the number someone is most likely to ask about. A dental practice in Jupiter would put the service, the town and the booking route in the same spot.

A dated section header

The API guides section opens with "Checked against the live API on 2026-10-11." The date tells a reader how fresh the prices are, and it gives us a single line to update when we recheck. Undated numbers in an index file are how stale prices spread from one assistant answer to the next.

Optional, used on purpose

Our Optional section holds the IP registry, the agency and the SEO practice. They are real pages, but they are not what a developer asking about endpoints needs. Filing them under Optional keeps the core list short without hiding anything.

The guards that keep it current

Short files drift quietly. On this site, scripts/verify-site.mjs fails when any guide or note is missing from llms.txt, when llms.txt stops pointing at llms-full.txt, when the full-text file grows past 500 KB, or when a banned unverifiable claim appears in either file. This note could not ship until its own entry was added to the index. Jason Colapietro's view is that an index nobody tests turns into a list of things that used to be true.

How to tell whether anything reads it

The plain answer first: no major search engine has said it ranks pages with llms.txt, and Google's search team has said Google Search does not use it. The file earns its keep through direct fetches. A developer pastes the URL into a coding assistant, an agent framework checks for it before crawling, or an answering tool fetches the root of a site it has already chosen to cite. Three checks tell you which of those is happening for you:

  1. Search your server logs for requests to /llms.txt and /llms-full.txt, and record the user agents and the dates.
  2. Paste the file URL into two or three assistants and ask a question only the file answers, such as a price or a service area. A wrong answer points at a weak note.
  3. Run an AI readiness check. Suede Scan's explainer on what an AI readiness score measures shows where llms.txt sits among the other signals.

The pattern carries well beyond developer docs. Suede DNA's article on structured data for a guitar rig archive shows a music archive where llms.txt, the sitemap and the robots tag all read one rule, so the three can never disagree about which pages count.

The tradeoffs

Notes that carry facts take longer to write and must change whenever a price or a page changes; a sitemap-style file never goes stale because it says nothing. Every date in the file creates recheck work. And llms.txt repeats facts your pages already state, so you need a test or a generator to keep the two in step. Suede accepts that cost because one stale price in an agent's answer is harder to correct than one extra line of maintenance.
